# joule-agent

## What this is
A benchmark + optimization tool that measures and improves tokens-per-joule on LLM inference servers (starting with vLLM on NVIDIA GPUs). It reads live serving-engine metrics and GPU power/clock telemetry, and recommends (later: applies) clock/power settings that cut energy per token without hurting latency.

This repo is the **open-source single-node agent** — the free "doorway" product. It is NOT the fleet-level control plane (that's a future, closed, paid product — don't build fleet orchestration, RBAC, multi-tenant SLO enforcement, or a calibration database here).

## The one question this repo exists to answer
**Does dynamic, phase-aware clock control beat a well-tuned STATIC clock lock by more than ~10% tokens-per-joule, at equal p99 latency, on real inference traffic?**

- If the answer is no → this becomes a benchmark report and a portfolio piece. Fine outcome.
- If yes → this becomes the doorway into a company.

Everything we build should serve getting an honest, reproducible answer to that question — not impress anyone, not guess, not oversell.

## v1 target (the whole first milestone)
A single CLI command:

```
joule benchmark --endpoint http://localhost:8000
```

Producing a report shaped like:

```
Current energy:       4.8 joules/token
Suggested SM clock:   1410 MHz
Estimated reduction:  11.7%
Observed throughput:  unchanged
P99 latency change:   +1.8%
```

The comparison MUST include, as named baselines (not just "before/after"):
1. Stock/default GPU behavior (no clock changes)
2. Best static clock lock found via sweep (`nvidia-smi -lgc`) — THIS is the real baseline to beat, not stock default
3. Our dynamic/phase-aware controller
4. NVIDIA Workload Power Profiles, if available on the hardware (optional, nice-to-have)

## Core components to build, in order
1. **Telemetry sampler** — implemented in `joule_agent/telemetry.py` (read-only NVML); one verification gate outstanding, below. Deviates from the original plan of a fixed ~50–100ms poll: on the local RTX 3060 Ti (driver 595.71.05) `nvmlDeviceGetPowerUsage()` refreshes only ~500ms, so polling faster just repeats values and fakes resolution the sensor doesn't have. Instead the recorder drains the driver's own sample ring (`nvmlDeviceGetSamples`) with a `lastSeenTimeStamp` cursor and writes every sample raw with its driver timestamp — resampling is an analysis-time decision, not a collection-time one. Clocks and the energy counter have no driver buffer and are still polled. Output per run: per-stream CSVs + `polled.csv` + `meta.json`. Sensor cadence and ring depth are per-device/per-driver properties, never hard-coded: `characterize_sensors()` measures them at startup and stamps them into each run's `meta.json` (expect the H100/H200 to differ). Full rationale is in the module docstring — keep it there, not duplicated here.
   - **Energy source of truth (gate CLOSED on the 3060 Ti, must be re-run per GPU):** `nvmlDeviceGetTotalEnergyConsumption()` is the source for run-level joules. It reads the same sensor chain as the power stream — it gives gap-free integration, not independent evidence of sensor fidelity. `verify_energy_agreement()` cross-checks it against a trapezoidal integration of the ~20ms power buffer. Results on the 3060 Ti:

     | condition | mean power | counter vs integrated |
     |---|---|---|
     | idle (flat ~21 W) | 21 W | 0.17% |
     | 0.5 Hz square, 67→169 W swing | 110 W | 0.18% |
     | 2.5 Hz square | ~110 W | 0.18% |
     | 5.0 Hz square | ~110 W | 0.09% |

     The idle row alone proves nothing — on a constant signal every integration method agrees, so it only confirms unit conversions and cursor logic. The oscillating rows are the real gate: verified swing of 101.8 W (89% of mean, σ 44.3 W) with the drive frequency recovered from the trace. Agreement holds to <0.2% through 5 Hz, well past the sub-second regime the dynamic controller will operate in. Load generated by `tools/synthetic_gpu_load.py` (ctypes + PTX via the driver API — no CUDA toolkit, no torch, so it runs unchanged on a rented H100). **Re-run this gate on every new GPU before trusting its joules** — agreement here is not agreement there, and a synthetic FMA load is not inference traffic.
2. **Workload signal reader** — implemented in `joule_agent/workload.py`, written against frozen fixtures in `tests/fixtures/vllm-0.26.0/` (176 real scrapes, never guessed metric names). Key finding: **the workload-composition signal already exists in vLLM's own metrics** — `num_requests_running` vs `num_requests_waiting` is the queue-pressure input the dynamic controller will read, with `num_requests_waiting_by_reason{reason="capacity"}` attributing the cause. Batch composition comes from diffing `prompt_tokens_total` vs `generation_tokens_total` across two scrapes: a prefill *share*, not a phase flag, since chunked prefill mixes both in one iteration. On the local fixtures prefill is ~14% of tokens but only ~1.8% of engine time — parallel prefill vs sequential decode.
   - **Signal provenance is typed, not assumed.** Every expected metric carries an `Exercise` state: `EXERCISED`, `LOW_RANGE_ONLY`, `PRESENT_UNEXERCISED`, or `ABSENT`. The middle two are the dangerous ones — a metric that parses cleanly and never errors but whose non-zero behaviour has never been observed here. `kv_cache_usage_perc` is `LOW_RANGE_ONLY` (max ~0.5%); `num_preemptions_total` is `PRESENT_UNEXERCISED` (flat zero everywhere). Snapshots carry these caveats in `.unvalidated` alongside the data, same pattern as the sampler's `possible_sample_loss`. States are re-established per hardware — see the H100 checklist in `serve_flags.txt`.
   - Expected metrics live in one module-level `EXPECTED_METRICS` constant so a vLLM version bump yields a reviewable diff, not silent `None`s.
3. **Load generator** — implemented in `joule_agent/loadgen.py`; **verification gate CLOSED on the 3060 Ti.** Validated live against vLLM 0.26.0: `steady` and `bursty` both delivered their full schedule (120/120 and 194/194 requests, max arrival lateness 3.2 ms — the client was never the bottleneck) with 107–117 `/metrics` samples collected per run. Reproducibility proven end-to-end, not just in unit tests: the same seed produced an identical `Schedule.digest()`, identical request count and identical offered-load CV across separate live runs, while a different seed produced a different plan. Digests are pinned as literals in `tests/test_loadgen.py`. **Noise floor worth knowing:** under bit-identical traffic, achieved queue metrics still varied ~2% run to run (13.39 s vs 13.67 s at non-zero waiting) — that is server-side variance and it bounds what a sweep can resolve, so a 10% effect is detectable but a 2% one is not. Deviates from the original plan of wrapping vLLM's `benchmark_serving.py`: it is a standalone stdlib-only implementation, because the sweep needs reproducibility guarantees that script does not provide. The load-shape decision is enforced in the type system rather than left to discipline: **open loop** (`ArrivalProcess` → a pre-materialised `Schedule`; every arrival time, prompt and output length is drawn from one seeded RNG *before* the run, so same seed + preset → same `Schedule.digest()`) vs **closed loop** (`ClosedLoop`, N workers firing back-to-back — offered load is a function of server response time, so a faster clock config receives *more* traffic and the comparison confounds the config change with the traffic change it induces). Closed-loop presets are kept only because they reproduce the `tests/fixtures/vllm-0.26.0/` capture conditions (`saturated` = `--max-num-seqs 4`) and are marked `reproducible=False`. Full rationale is in the module docstring — keep it there, not duplicated here. Depends on `read_snapshot` from `joule_agent.workload`; CLI is `python -m joule_agent.loadgen` (`--preset/--seed/--duration/--rate-scale/--out/--list-presets`).
   - **Variation is a harness requirement, not a nice-to-have.** Dynamic control can only win where variation exists, so a harness offering only steady traffic structurally biases the kill test toward a "no" that is an artifact of the harness rather than the physics. Presets therefore include Poisson arrivals and an on/off burst cycle with real idle gaps (`steady` / `poisson` / `bursty` / `bursty_heavy`), and `RunReport.offered_load_cv` records the variation actually delivered — so a "static wins" result can be checked against whether the traffic ever varied.
   - **Intended vs achieved, same honesty pattern as the sampler's `possible_sample_loss` and the workload reader's `Exercise` states.** A preset named "saturated" is an intention, not evidence. Every run polls `/metrics` and reports what happened: `time_at_nonzero_waiting_s`, `achieved_saturation`, `max_waiting`/`max_running`, and `schedule_achieved` (arrivals fired within 250ms of plan — large lateness means the *client* shaped the traffic, not the server). Warnings fire when a preset intends saturation and the queue never left zero, or when offered-load CV is below 0.05.
4. **Static sweep runner** — iterate `nvidia-smi -pl <watts>` and `nvidia-smi -lgc <mhz>` settings, run the load generator at each, log tokens/sec, joules/token, p50/p95/p99 latency, SLO-violation rate. Find the best static point. THIS IS A REQUIRED BASELINE, not optional. **Contract inherited from component 3: it must refuse any preset with `reproducible=False`, and `Schedule.digest()` must be identical across every run of a sweep — otherwise the configs were not compared under the same traffic.**
5. **Dynamic controller (simple first)** — a control loop: read workload signal → decide a clock/power target based on current batch composition and remaining latency headroom → apply via NVML → measure → repeat sub-second. Start with a dumb/simple rule. Don't over-engineer the policy before we have data.
6. **Benchmark/report engine** — runs all baselines back-to-back on the same workload, outputs the CLI report above plus a CSV/JSON of raw samples and a before/after plot (matplotlib is fine).
7. **Safety boundaries** — hard clock floor (never lock below a safe minimum), always restore default clocks/power on exit or crash (register cleanup handlers), refuse to run without explicit `--i-understand-this-changes-gpu-hardware-settings` type confirmation flag the first time.

## Non-negotiable safety/honesty rules
- Never claim a specific efficiency percentage in code comments, README, or CLI output that hasn't actually been measured in that run. No placeholder "20-30%" claims anywhere.
- Report savings as a curve against p99 degradation, never a single point number in isolation.
- Always compare against tuned-static, never just stock default — beating stock default proves nothing.
- Auto-restore GPU clocks to default on any exit path (including Ctrl+C, exceptions).
- NVML clock/power writes require root/admin — fail with a clear error message if not running with sufficient privileges, don't silently no-op.

## Stack / language
- Python only for v1. No Rust, no Go, no C++ yet — the interesting part right now is the control policy, not the runtime performance of the control loop itself (100ms–1s loop, Python is plenty fast).
- Key libs: `pynvml` (install the official `nvidia-ml-py` package, not the third-party `pynvml` one — both provide a module named `pynvml`), `matplotlib` for plots. Note: the HTTP/parsing side has stayed stdlib so far — `workload.py` parses the Prometheus text format directly (no `prometheus-client`) and `loadgen.py` uses `urllib.request` (no `requests`), so neither has been needed yet — add either only when something actually requires it. vLLM's own benchmark scripts remain useful as *reference*, but component 3 chose not to depend on them (see above).
- Target GPU for local dev: whatever's available (e.g. RTX 3060 Ti) for plumbing/wiring only — it's underpowered and power-locked, so don't expect a representative number locally. The real number comes from a rented H100/H200 (RunPod/Lambda/Vast).
