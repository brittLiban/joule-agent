# joule-agent

## What this is
A benchmark + optimization tool that measures and improves tokens-per-joule on LLM inference servers (starting with vLLM on NVIDIA GPUs). It reads live serving-engine metrics and GPU power/clock telemetry, and recommends (later: applies) clock/power settings that cut energy per token without hurting latency.

This repo is the **open-source single-node agent** — the free "doorway" product. It is NOT the fleet-level control plane (that's a future, closed, paid product — don't build fleet orchestration, RBAC, multi-tenant SLO enforcement, or a calibration database here).

## The one question this repo exists to answer
**Does dynamic, phase-aware clock control beat a well-tuned STATIC clock lock by more than ~10% tokens-per-joule, at equal p99 latency, on real inference traffic?**

- If the answer is no → this becomes a benchmark report and a portfolio piece. Fine outcome.
- If yes → this becomes the doorway into a company.

Everything we build should serve getting an honest, reproducible answer to that question — not impress anyone, not guess, not oversell.

## v1 target (the whole first milestone)
A single CLI command:

```
joule benchmark --endpoint http://localhost:8000
```

Producing a report shaped like:

```
Current energy:       4.8 joules/token
Suggested SM clock:   1410 MHz
Estimated reduction:  11.7%
Observed throughput:  unchanged
P99 latency change:   +1.8%
```

The comparison MUST include, as named baselines (not just "before/after"):
1. Stock/default GPU behavior (no clock changes)
2. Best static clock lock found via sweep (`nvidia-smi -lgc`) — THIS is the real baseline to beat, not stock default
3. Our dynamic/phase-aware controller
4. NVIDIA Workload Power Profiles, if available on the hardware (optional, nice-to-have)

## Core components to build, in order
1. **Telemetry sampler** — implemented in `joule_agent/telemetry.py` (read-only NVML); one verification gate outstanding, below. Deviates from the original plan of a fixed ~50–100ms poll: on the local RTX 3060 Ti (driver 595.71.05) `nvmlDeviceGetPowerUsage()` refreshes only ~500ms, so polling faster just repeats values and fakes resolution the sensor doesn't have. Instead the recorder drains the driver's own sample ring (`nvmlDeviceGetSamples`) with a `lastSeenTimeStamp` cursor and writes every sample raw with its driver timestamp — resampling is an analysis-time decision, not a collection-time one. Clocks and the energy counter have no driver buffer and are still polled. Output per run: per-stream CSVs + `polled.csv` + `meta.json`. Sensor cadence and ring depth are per-device/per-driver properties, never hard-coded: `characterize_sensors()` measures them at startup and stamps them into each run's `meta.json` (expect the H100/H200 to differ). Full rationale is in the module docstring — keep it there, not duplicated here.
   - **Energy source of truth (gate CLOSED on the 3060 Ti, must be re-run per GPU):** `nvmlDeviceGetTotalEnergyConsumption()` is the source for run-level joules. It reads the same sensor chain as the power stream — it gives gap-free integration, not independent evidence of sensor fidelity. `verify_energy_agreement()` cross-checks it against a trapezoidal integration of the ~20ms power buffer. Results on the 3060 Ti:

     | condition | mean power | counter vs integrated |
     |---|---|---|
     | idle (flat ~21 W) | 21 W | 0.17% |
     | 0.5 Hz square, 67→169 W swing | 110 W | 0.18% |
     | 2.5 Hz square | ~110 W | 0.18% |
     | 5.0 Hz square | ~110 W | 0.09% |

     The idle row alone proves nothing — on a constant signal every integration method agrees, so it only confirms unit conversions and cursor logic. The oscillating rows are the real gate: verified swing of 101.8 W (89% of mean, σ 44.3 W) with the drive frequency recovered from the trace. Agreement holds to <0.2% through 5 Hz, well past the sub-second regime the dynamic controller will operate in. Load generated by `tools/synthetic_gpu_load.py` (ctypes + PTX via the driver API — no CUDA toolkit, no torch, so it runs unchanged on a rented H100). **Re-run this gate on every new GPU before trusting its joules** — agreement here is not agreement there, and a synthetic FMA load is not inference traffic.
2. **Workload signal reader** — implemented in `joule_agent/workload.py`, written against frozen fixtures in `tests/fixtures/vllm-0.26.0/` (176 real scrapes, never guessed metric names). Key finding: **the workload-composition signal already exists in vLLM's own metrics** — `num_requests_running` vs `num_requests_waiting` is the queue-pressure input the dynamic controller will read, with `num_requests_waiting_by_reason{reason="capacity"}` attributing the cause. Batch composition comes from diffing `prompt_tokens_total` vs `generation_tokens_total` across two scrapes: a prefill *share*, not a phase flag, since chunked prefill mixes both in one iteration. On the local fixtures prefill is ~14% of tokens but only ~1.8% of engine time — parallel prefill vs sequential decode.
   - **Signal provenance is typed, not assumed.** Every expected metric carries an `Exercise` state: `EXERCISED`, `LOW_RANGE_ONLY`, `PRESENT_UNEXERCISED`, or `ABSENT`. The middle two are the dangerous ones — a metric that parses cleanly and never errors but whose non-zero behaviour has never been observed here. `kv_cache_usage_perc` is `LOW_RANGE_ONLY` (max ~0.5%); `num_preemptions_total` is `PRESENT_UNEXERCISED` (flat zero everywhere). Snapshots carry these caveats in `.unvalidated` alongside the data, same pattern as the sampler's `possible_sample_loss`. States are re-established per hardware — see the H100 checklist in `serve_flags.txt`.
   - Expected metrics live in one module-level `EXPECTED_METRICS` constant so a vLLM version bump yields a reviewable diff, not silent `None`s.
3. **Load generator** — implemented in `joule_agent/loadgen.py`; **verification gate CLOSED on the 3060 Ti.** Validated live against vLLM 0.26.0: `steady` and `bursty` both delivered their full schedule (120/120 and 194/194 requests, max arrival lateness 3.2 ms — the client was never the bottleneck) with 107–117 `/metrics` samples collected per run. Reproducibility proven end-to-end, not just in unit tests: the same seed produced an identical `Schedule.digest()`, identical request count and identical offered-load CV across separate live runs, while a different seed produced a different plan. Digests are pinned as literals in `tests/test_loadgen.py`. **Noise floor worth knowing:** under bit-identical traffic, achieved queue metrics still varied ~2% run to run (13.39 s vs 13.67 s at non-zero waiting) — that is server-side variance and it bounds what a sweep can resolve, so a 10% effect is detectable but a 2% one is not. Deviates from the original plan of wrapping vLLM's `benchmark_serving.py`: it is a standalone stdlib-only implementation, because the sweep needs reproducibility guarantees that script does not provide. The load-shape decision is enforced in the type system rather than left to discipline: **open loop** (`ArrivalProcess` → a pre-materialised `Schedule`; every arrival time, prompt and output length is drawn from one seeded RNG *before* the run, so same seed + preset → same `Schedule.digest()`) vs **closed loop** (`ClosedLoop`, N workers firing back-to-back — offered load is a function of server response time, so a faster clock config receives *more* traffic and the comparison confounds the config change with the traffic change it induces). Closed-loop presets are kept only because they reproduce the `tests/fixtures/vllm-0.26.0/` capture conditions (`saturated` = `--max-num-seqs 4`) and are marked `reproducible=False`. Full rationale is in the module docstring — keep it there, not duplicated here. Depends on `read_snapshot` from `joule_agent.workload`; CLI is `python -m joule_agent.loadgen` (`--preset/--seed/--duration/--rate-scale/--out/--list-presets`).
   - **Variation is a harness requirement, not a nice-to-have.** Dynamic control can only win where variation exists, so a harness offering only steady traffic structurally biases the kill test toward a "no" that is an artifact of the harness rather than the physics. Presets therefore include Poisson arrivals and an on/off burst cycle with real idle gaps (`steady` / `poisson` / `bursty` / `bursty_heavy`), and `RunReport.offered_load_cv` records the variation actually delivered — so a "static wins" result can be checked against whether the traffic ever varied.
   - **Intended vs achieved, same honesty pattern as the sampler's `possible_sample_loss` and the workload reader's `Exercise` states.** A preset named "saturated" is an intention, not evidence. Every run polls `/metrics` and reports what happened: `time_at_nonzero_waiting_s`, `achieved_saturation`, `max_waiting`/`max_running`, and `schedule_achieved` (arrivals fired within 250ms of plan — large lateness means the *client* shaped the traffic, not the server). Warnings fire when a preset intends saturation and the queue never left zero, or when offered-load CV is below 0.05.
4. **Static sweep runner** — implemented in `joule_agent/sweep.py`; **never yet run against a serving engine.** Iterates clock and power settings, replays the load generator at each, and records tokens/sec, joules/token, p50/p95/p99 latency and SLO-violation rate to find the best static point. THIS IS A REQUIRED BASELINE, not optional. All clock/power changes go through `joule_agent.gpu_guard` — no direct NVML writes, no shelling out to `nvidia-smi`. Full rationale is in the module docstring; four decisions are load-bearing and are summarised here only because they change what the numbers mean.
   - **One `Schedule` object, built once, replayed at every point.** The contract inherited from component 3 — refuse `reproducible=False`, identical digest across the sweep — is met **by construction** rather than by convention: the runner does not rebuild the schedule per point, it replays the same object. It still asserts the digest per run, because a construction argument is not a measurement, and a mismatch **aborts and voids the sweep** rather than warning. Closed-loop presets are refused at the CLI and again in the constructor.
   - **Arm the guard per point; the stock point arms nothing.** `gpu_guard` exposes no unlock, only `restore`, so a stock reference cannot exist inside one armed session. Rather than add an unlock to the module whose whole design is to have as few hardware-touching paths as possible, each locked point arms → writes → measures → restores, and stock runs unguarded, which the guard's own contract covers ("a guard that never writes releases the claim on exit without resetting clocks"). Every point therefore starts from verified stock, and a crash strands one point's lock rather than the sweep's.
   - **A failed restore aborts the whole sweep.** `_check_not_busy` would refuse the next arm anyway; making it explicit means the partial results say why they are partial. A sweep that continues past a failed restore is measuring a card in an unknown state.
   - **Repeats are round-robin, and stock is the drift detector.** At component 3's ~2% noise floor a single run per configuration makes the best point partly a noise draw, so points repeat (default 3) and rounds interleave. But interleaving *hides* drift rather than measuring it — so stock, which recurs every round and is by definition the same configuration each time, is compared against itself across rounds and reported as `stock_drift_pct`. Above the noise floor it warns that between-configuration differences of that size are not attributable to the configuration. For the same reason the best point is chosen by **overlapping intervals, not bare argmax**: points within one standard deviation (or the 2% floor, whichever is larger) of the best are reported `tied`, because naming one of them best asserts a distinction the measurement cannot support.
   - **Requested clock is not achieved clock.** Every run samples the SM clock and records `achieved_clock_median_mhz` beside `requested_clock_mhz`. Two points that requested different clocks and achieved the same one are one configuration measured twice, and the sweep says so — nothing else in the pipeline would catch a device that snaps to clock bins.
   - **Honesty fields, same pattern as components 1–3.** `bracket_skew_ms` measures the gap between the token bracket and the energy bracket instead of assuming it cancels (5.81 ms on a 1.6 s dry run). A backwards energy counter or a restarted vLLM voids that run rather than producing a negative or a fabricated number. An SLO-violation rate over zero completed requests is `None`, never `0.0` — which would read as a configuration that met the SLO perfectly.
   - **SLO threshold**: `--slo-ms` if given, else derived from the stock point's median p99 × `--slo-slack` (default 1.10), with `slo_threshold_source` recorded either way. The project question is "at equal p99 latency"; 10% is the defensible reading of "equal" at a 2% noise floor.
   - **Review pass 1 (`hardware-safety-reviewer`) returned 4 BLOCKING findings, and two of them meant the locked path had never executed once — on hardware or in tests.** (1) `check_stale_state` was called as `(state_path, index=…)` against a signature of `(controller, state_path)`: an uncaught `TypeError`, so every sweep with `--clocks` died on a traceback and the guard-contract pre-flight the module's own docstring leans on had never run. (2) One `NvmlGpuController` was shared across points, but `_ClaimMixin.claim` refuses a second owner and **nothing ever releases `_claimed_by`** — so point 2 was refused, and every locked sweep would have degraded to *one point, then abort*, with a message falsely warning the GPU may still be modified. Reproduced directly before fixing. Fixed with a fresh controller per point; releasing the claim instead would have meant editing the protected surface. (3) A hardware write landed **before** the clock-floor refusal: `--clocks 100 --power-limits-w 150` capped power, then raised `ClockFloorError` — the same defect shape `gpu_guard` fixed inside itself in pass 12, reintroduced one layer out. The floor is now an argument-only refusal in `main()`, checked again before the guard is constructed, and `lock_clocks` runs before `set_power_limit_mw`. (4) `controller.close()` ran unconditionally in a `finally`, shutting NVML down even after a failed restore — turning the `atexit` last-chance restore into a certain failure against a dead handle. Both `gpu_guard.main()` and `verify_clock_lock.py` guard against this by name; `sweep.py` did not, and *structurally could not*, because arm-per-point means `main()` holds no guard reference. `SweepRunner.hardware_may_be_modified` now carries it out.
   - **The `_restored` flag is safe to read after a failed `__enter__`, and that is not an accident.** It initialises **True** and flips to False only in `_mark_touched`, at the first real hardware write — so a guard refused at arm time reports nothing modified, and only a guard that actually wrote and failed to restore raises the alarm. Reading it any earlier in its lifecycle would have made every refusal cry wolf.
   - **Two HIGH findings, both about not saying more than is known.** `GpuGuardError` was caught as one class, so a *refusal* — `ConsentError`, `PrivilegeError`, `ClockFloorError`, `GuardBusyError`, all of which prove nothing was written — produced "the GPU may still be modified". Given finding (2) that would have been the *common* case on real hardware: cry-wolf on the one message that has to be believed. And an **aborted** sweep still named a `best_point` and wrote it to a durable JSON — including on the digest-mismatch path whose own error says "every number in this sweep is void". Aborted sweeps now name no winner, and unequal repeat counts warn rather than being silently averaged.
   - **The test audit found 11 issues, including three tests that certified nothing.** The worst was the one guarding provenance: `assert len(h) == 64` is true of *any* sha256, so the `gpu_guard_sha256` field could have hashed **b""** and passed — the field whose entire purpose is answering "is this the code that was measured?". Also: `assert calls == []` for "the stock point never constructs a guard" was satisfied by the point never running at all; a metrics-failure test was satisfied by a *different* code path emitting a similar string, so deleting the recording path it named left it green; the drift threshold's `abs()` was unpinned, so a card getting **cheaper** mid-sweep would have gone unwarned; and the tie band's standard-deviation half was untested because every fixture had zero variance. All fixed, each with the specific mutation named in the test docstring. `NOISE_FLOOR_FRACTION` survived being set to **0.08** — the constant deciding which benchmark differences are real could be 4x wrong unnoticed — so it is now pinned directly.
   - **The auditor corrected its own instrument mid-run, which is the reason to trust the rest.** Its first batch reported a test as surviving a mutation; the batch had served stale `__pycache__` bytecode, so the interpreter never compiled the mutation. Stale bytecode makes a mutation *invisible*, so its failure mode is a spurious **survive**, never a spurious fail — every kill stood, every survivor needed rechecking. Same class as the standing rule below: a mutation that never reached the code proves exactly as little as one that misses the property.
   - **Review pass 2 returned 2 more BLOCKING findings, both in code pass 1's fixes had introduced or reordered.** That is the fifth time in this repo a fix has created a defect, and the first outside `gpu_guard`. (1) The new `preflight_stale` probe constructed `NvmlGpuController(index=args.gpu)` **unwrapped**, so a mistyped `--gpu` surfaced as a raw `NVMLError` traceback rather than a refusal — `gpu_guard._controller()` exists precisely because that bug reached committed code there, and the sampler eight lines below was already wrapped. Unreachable by the new contract check, too: the root refusal returns before that line, and every check in that tool is unprivileged by design. (2) Reordering `lock_clocks` before `set_power_limit_mw` made an existing message **false**. `_write` translates NVML `NoPermission` into `PrivilegeError`, which is a *refusal* class — so a device that accepts the clock lock and then refuses the power write recorded "Nothing was written to the GPU" while a lock had landed and been undone. The end state was safe; the durable artifact lied. Fixed by recording what actually reached the device (`_point_writes`) rather than inferring it from the exception class, which is the only version that survives either write order.
   - **Also from pass 2, and the answer to a question I had asked wrongly.** `pthread_sigmask` is **per-thread**, so the sampler thread was the real lifecycle hazard, not the NVML session count (NVML's init is refcounted; N outstanding sessions are harmless). The sampler was started and stopped without `try/finally`, so a raise from the load generator left it polling through `guard.__exit__` → `restore()` — a live thread with SIGINT/SIGTERM unblocked can take a delivery that `gpu_guard`'s signal-blocked sections exist to defer, and the handler then runs on the main thread inside the window it was protecting. Narrowed race, not a certain failure, and now closed. Separately: `build_grid` crossed power limits only inside `for clk in clocks`, so `--power-limits-w` with no `--clocks` built a stock-only grid — the operator was pushed through consent, root and the stale pre-flight, waited out the full run, and **not one power limit was applied**. `writes_hardware` is now derived from the grid rather than the arguments, since the two had silently diverged.
   - **The same claim defect was then written a third time, into `verify_clock_lock.py`, and only real hardware caught it.** The multi-target rewrite gave each target a fresh `GpuGuard` but shared one controller, so the run died at target 2 with `controller already claimed by <GpuGuard …>` — after target 600 had measured cleanly (600/600/600 MHz at 100% utilization, so the new load-liveness check works). Nothing was left modified: the refusal fires in `arm()`, before any write, and the first guard had restored. The loop lived entirely in `main()` where no test could reach it, so it is now `locked_phases_for()` at module level with two tests, one of which is mutation-verified to reproduce that exact error. **Per-guard controller ownership is a rule, not an optimisation** — three occurrences in two files is enough evidence.
   - **A fourth baseline, and the drift claim now has three samples.** 1935–1950, then 1905–1935, then **1860–1890** under load. The unlocked boost clock on this card moves ~4% across sessions — larger than the first two runs suggested and larger than the ~2% run-to-run noise floor. Stock is the noisy control, and that is an argument for the tuned-static baseline, not an obstacle to it.
   - **`tools/sweep_contract_check.py` closes the seam both blockers came through.** Neither was visible to 241 unit tests, because both lived in `main()` and no test imported it — the same seam `cli_contract_check.py` was built for after three defects reached committed code through it in `gpu_guard`. 24 subprocess checks, all runnable **unprivileged**, asserting exit code, message content, and — the load-bearing part — that every refusal path leaves **no guard state file at all**, since arming publishes a claim and a caller that was never allowed to write must never have claimed the device. The logic `main()` alone could reach is also being moved out of it: `preflight_stale()` is module-level and unit-tested precisely because its predecessor was not.
   - **Verification gate: OPEN — never run against vLLM.** Everything above is exercised by 26 unit tests against injected fakes plus one live stock-only dry run with no serving engine, which confirmed the NVML read path end to end: 210 MHz idle clock sampled, 31.39 J over 1.603 s from the energy counter (~19.6 W, the right order for an idle 3060 Ti — a plausibility check, not an agreement test; the real one is component 1's `verify_energy_agreement`). No number this produces is a measured result until it has run against a real engine — and until the multi-target lock-efficacy gate below closes, since a sweep is exactly the thing that gate protects.
5. **Dynamic controller (simple first)** — a control loop: read workload signal → decide a clock/power target based on current batch composition and remaining latency headroom → apply via NVML → measure → repeat sub-second. Start with a dumb/simple rule. Don't over-engineer the policy before we have data.
6. **Benchmark/report engine** — runs all baselines back-to-back on the same workload, outputs the CLI report above plus a CSV/JSON of raw samples and a before/after plot (matplotlib is fine).
7. **Safety boundaries** — **BUILT EARLY, OUT OF ORDER, DELIBERATELY.** Implemented in `joule_agent/gpu_guard.py` *before* component 4, because component 4 is the first code that writes to the GPU and a safety net living inside the code it protects is not a net — the first buggy draft of the sweep would run on real hardware with nothing underneath it. **Every clock/power write in this repo goes through `gpu_guard`. Nothing else may call `nvmlDeviceSetGpuLockedClocks`, `nvmlDeviceSetPowerManagementLimit`, `nvidia-smi -lgc` or `nvidia-smi -pl`.** Contract: whatever happens — clean exit, exception, SIGINT, SIGTERM, hard kill — the GPU returns to stock. Context manager is the primary API, backed by `atexit` + signal handlers, re-entrant, idempotent restore. Clock floor (`MIN_SM_CLOCK_MHZ = 300`) **refuses**, never silently clamps. Consent flag `--i-understand-this-changes-gpu-settings` gates the first write in a process; reads never require it. Missing root fails loudly, never a silent no-op. Argument validation runs *before* the privilege check so a bad clock value is reported as such rather than sending an operator to `sudo` first.
   - **Protected surface vs outer surface.** The convergence bar is *not* "no findings anywhere" — six review passes showed that chasing every finding produced fixes that introduced worse defects than they retired. The bar is **zero findings in the protected surface**: every code path involved in snapshot, hardware write, restore, stale detection, and recovery — anything that can touch hardware state, or the evidence about hardware state. The **outer surface** (CLI ergonomics, status formatting, advisory text) is allowed to be imperfect; findings there are recorded below as known-and-accepted rather than fixed. The restore guarantee is not allowed to be imperfect.
   - **Device identity is checked before any restore applies a snapshot (protected surface).** A record carries `device_index` *and* `device_uuid`, and `_device_mismatch()` gates both recovery and stale detection. **UUID is authoritative; index is not an identity** — it is an enumeration order that shifts across a reboot, a driver reload, or a `CUDA_VISIBLE_DEVICES` change, so a record can name index 0 and mean a different physical card. A UUID mismatch is refused even when the index matches; a UUID match is accepted even when the index moved. Before this existed, `check_stale_state`'s own recommendation omitted `--gpu` and `main()` defaults it to 0, so **following the module's advice exactly would apply GPU 1's snapshot to GPU 0** — mis-capping the wrong card, clearing the right card's record, and exiting 0. On a homogeneous node NVML accepts the foreign value silently. **Live-verify on rental day: the H100 node will likely be multi-GPU, and this path has only ever been exercised against the fake NVML layer.** See the H100 checklist in `serve_flags.txt`.
   - **The claim is published at `arm()`, not at first hardware touch (protected surface).** `_check_not_busy()` can only see what is on disk. While the record appeared only on the first write, a second process read a clean file during that window and armed too; both then held "stock" snapshots and both wrote the file wholesale, so the later record **erased the earlier one** — and a record saying `power_limit_written_mw: null` tells recovery to leave a cap the first guard really did apply. `arm()` now writes `restored: false` before returning. That field means *"a guard holds this device"*, not *"the hardware is modified"* — only the first is knowable at arm time, and the record's own `clocks_locked` / `power_limit_written_mw` carry the second, which is what recovery reads. A guard that never writes releases the claim on exit **without resetting clocks**: it must not touch a device it never modified.
   - **`restored: true` means the debt is settled, not that it is still owed (protected surface).** Nothing clears `power_limit_written_mw` on a successful restore, so a finished run leaves a clean record that still names its historical write. Recovery read that field alone and **replayed the snapshot's old limit over whatever the operator set afterwards**, reporting success. It now also requires `restored` to be false; a record that cannot say it owes anything does not authorise a hardware write.
   - **Unverifiable identity is not verified identity (protected surface).** A record carrying a UUID was written by a guard that could read one, so if the live UUID read fails the identity is *unknowable*, not *matching*. The comparison used to fall through to the index — accepting precisely the case the UUID exists to catch, since after a re-enumeration the indexes match and mean different cards. It now refuses. Fail-closed is not fail-stuck: the unconditional clock reset still applies, and `--force-power-default` still lifts the cap using *this* card's own default without applying anyone else's snapshot or clearing the record.
   - **Pass 7 (`hardware-safety-reviewer`, at `70859fa`) returned 7 findings; pass 8 fixed 6 and accepted 1.** Fixed: `_write_state` was re-enterable from a signal handler, so an interrupted outer frame could republish stale content over the newer truth — worst case the `restore_failed` record, the only evidence a still-modified GPU exists (now signal-blocked, with a unique temp name as defence in depth); `_install_handlers` re-read `signal.getsignal()` on a second install and recorded **its own handler** as "previous", so `_signal_restore` chained into itself unbounded — the process survived a SIGTERM it was meant to die from (recording is now once-only); surrendering the claim left `_armed` True with nothing on disk, so a reused guard object could write hardware having never re-run `_check_not_busy` (now disarms); `check_stale_state` reported "cannot tell" as "other card" and prescribed the `--gpu N` its own code calls worthless; `--force-power-default` set its success flag before checking that the default read succeeded, reporting a write it never made with exit 0; and the dead-pid refusal asserted "the GPU may still be modified" about arm-only records that state the opposite. Consent is now checked *before* auto-arming, so a refused caller leaves no claim.
   - **Accepted, not fixed:** recovery resets clocks even when the record names no hardware change. That is the same unconditional belt-and-braces reset that runs with *no* state file at all — a deliberate, tested behaviour (`test_recovery_resets_clocks_even_with_no_state_file`), not a new hazard introduced by arm-time publishing.
   - **A reviewer's finding is a claim, not a verdict.** Pass 7's F4 said no command can clear a valid-but-foreign record. Half true: for a *provably* foreign record `restore --gpu <recorded index>` resolves it, and the proposed fix — letting `_check_not_busy` skip records for other cards — would have been a **new defect**, since `arm()` publishes a whole document with no merge and would have erased that card's evidence. One state file holds one record; guarding several devices means giving each its own `--state-path`.
   - **Pass 8 (at `cde7330`) returned 3 findings; two were introduced by pass 8's own fixes.** That is the third time in this module's history that a review-driven fix created a new defect, and it is why the passes keep running. (1) `restore()` set the in-memory `restored` flag *before* the write that persists it, and returned quietly on failure — and since that same flag gates `_surrender_claim`'s write block, **every later restore path silently skipped the retry**: hardware back to stock, disk still saying it is modified, nothing anywhere correcting it. Both paths now roll the flag back; the in-memory flag must never claim more than the disk does. (2) Recording the previous signal handler *once* was wrong once the guard started disarming on surrender — an application installing its own handler between two `with` blocks had it overwritten and chained to a stale one. It now records whatever is really installed unless that is already the guard's own handler, which needs one stable bound object (`self._signal_restore` builds a new bound method per access, so `is` never matches). Both wrong directions — once-only and unconditional — are pinned by mutation, because unconditional is the pass-7 unbounded-recursion bug.
   - **`--gpu N` is not always a terminating instruction (protected surface).** When a UUID mismatch is proven *and* the record's own index still points at the live controller, the enumeration moved under the record: `--gpu <recorded index>` is the command that just failed, and repeating it loops forever. The recorded UUID is the only usable handle, so the advice now names `nvidia-smi --query-gpu=index,uuid --format=csv` and, if that UUID is absent from the machine, says plainly that the card is gone and only a human can retire the record. **Deliberately not automated:** a UUID→index lookup would need a new controller method, a fake-peer fixture, and NVML handles for cards this guard was never given — machinery bought to avoid writing a sentence, and it would still only cover the case where the card is present.
   - **Accepted (pass 8, flagged not counted):** `restore()`'s two hardware calls are not inside `_deferred_signals()` — only `_write_state` is. A signal whose previous handler returns normally can let the outer frame resume and republish a more pessimistic record over the inner's clean one. Conservative direction, pre-existing, and blocking signals across a possibly-hanging NVML reset is the deadlock class this module already paid to avoid. Same category: recovery refuses forever if the recorded pid number is reused by an unrelated process.
   - **Pass 10 (at `125012d`) found a BLOCKING regression introduced by pass 9 — the same defect class, one object over.** Pass 9 changed handler recording from "once only" to "unless it is mine", which excludes self-loops but **not another guard's handler**. Nothing uninstalled on disarm, so a disarmed guard's handler stayed installed and became the `current` the next guard recorded; after `a.arm / b.arm / a.restore / a.arm`, `_prev_handlers` is a 2-cycle and the chain call recurses without bound — process alive on a SIGTERM it should have died from, and if either restore is failing, hundreds of NVML resets and fsynced writes inside signal handling. **Three defects in the same eight lines across three passes** (unconditional → self-recursion; once-only → lost app handler; not-mine → two-guard cycle) is what finally forced the answer: `_chain_link` now records the other guard's *link* instead of the guard, which is inductively never a guard, so a cycle is unrepresentable rather than detected — no walk, no hop limit.
   - **The cost of that, stated because it is a real loss:** with two guards armed in one process, only the last to install runs on a signal; the earlier one no longer restores in-process and recovers through its state file instead. That degrades to the documented hard-kill path rather than to unbounded recursion, and nothing in this repo arms two guards at once. The module docstring says so where it recommends per-device state files.
   - **`restore()` and `_surrender_claim` now run their bookkeeping tails signal-blocked.** They issue no NVML call, so blocking cannot strand a Ctrl+C behind a hanging driver — and without it a handler landing between the flag and the write re-entered, disarmed, and returned, while the outer frame rolled back intending to stay armed.
   - **Second vacuous assertion caught by a reviewer, not by me.** `assert g._prev_handlers[sig] is not g._signal_restore` is unconditionally true, because bound methods are rebuilt per access — it passed under the very bug it claimed to catch, in a test recorded as mutation-verified. Compare `__func__`. Related: 25 tests in the suite arm a guard without restoring it, so signal dispositions leaked between tests and one test passed in the full run while failing alone. An autouse fixture now saves and restores SIGINT/SIGTERM around every test. **Mutation-verification does not prove a test is sound, only that it moves** — check that each assertion *can* be false.
   - **Pass 11 (at `aafa7e0`) found 2 more, both introduced by pass 10 — the fourth consecutive pass with a defect in the signal-handler code.** (1) `arm()` installed handlers, then set `_armed`; a signal in that window ran `_signal_restore` → `restore` → `_surrender_claim`, which *uninstalled* and set `_armed` False — and then the interrupted frame resumed and set `_armed` True. Armed with **no handlers**, and since every entry point short-circuits on `_armed`, nothing ever reinstalled: the next clock lock ran with no in-process restore path. Install/arm/publish is now one signal-blocked step. (2) `_signal_restore` handed the signal back unconditionally, including when `restore()` had *raised*. **This fix did not survive the pass-12 narrowing and is no longer in the code** — with no chain, a non-ignored signal always ends in `SIG_DFL` + `os.kill`, so the process dies on the first delivery and there is no second one to retry with. Accepted: a failed restore prints to stderr and leaves `restore_failed: true` on disk, which is the designed recovery path. The in-process retry survives only on the `SIG_IGN` path, which is the only one where the process outlives the handler. Also fixed: `min_clock_mhz=0` disabled invariant 3 entirely (a constructor argument could turn a refusal into a default — callers may now only *raise* the floor), and `_uninstall_handlers` passing a C-installed `None` to `signal.signal` raised `TypeError`.
   - **The trend is the finding.** Passes 7→11 each found new protected-surface defects, and passes 8, 10 and 11 found defects *created by the immediately preceding pass's fix* — every one of them in the same ~15 lines of signal-handler bookkeeping. Fixes elsewhere in the module (device identity, state-file semantics, power replay, the clock floor) have held on first attempt. **That localises the instability precisely**: it is not the guard, it is the handler chain. Two coverage gaps that let it persist are now closed — no test had ever delivered a real signal with two guards armed (the chain property was asserted structurally only), and none had called `_signal_restore` on a failing restore.
   - **The handler chain was REMOVED, not repaired — the second narrowing decision in this module's history, made on the same evidence as the first.** Chaining to the application's SIGINT/SIGTERM handler produced three defects across three passes, all from one question: what to record as "previous". Record unconditionally → the guard chained to itself, unbounded recursion. Record once only → a handler installed between two `with` blocks was lost. Record unless it is mine → two guards recorded each other, a 2-cycle, unbounded again. Each fix was correct for the bug it named and wrong for a case one step away. **The capability being served — "the application's handler still runs after the guard restores" — was never in this module's contract**; the contract is that the GPU returns to stock. So `_chain_link`, `_uninstall_handlers` and `_prev_handlers` are gone: nothing is recorded, nothing is called back, and a cycle is not expressible. A guard that is armed owns those two signals — **install your handler around the guard, not under it.**
   - **What survived the narrowing, and why:** a process that deliberately set `SIG_IGN` is still not converted into a death. That is about *whether to kill the process*, not about chaining, so it needs a lookup (`self._ignored`) and never a call. It is also the one path where the process survives the handler, which makes it the only place a second delivery can retry a failed restore — and the only path where an interrupted `arm()` frame ever resumes, which is what keeps `arm()`'s signal block load-bearing rather than decorative. Both are pinned by mutation.
   - **Cost, stated because it is real:** an application handler that would have run on SIGTERM no longer does. 9 tests were deleted — every one of them pinning a property this module never promised. In exchange, ~73 lines of the most defect-dense code in the repo are gone, along with the class of defect they generated.
   - **Pass 12 (at `66103a3`) found 4 more — and the most important one is that the narrowing did not remove the defect class it was justified by.** `_install_handlers` still asked *"is this handler mine?"*, which excludes only self-loops — the exact blind spot that took three passes to find in the deleted chain. The chain was gone so no cycle could form, but the **disposition lookup** inherited the same broken question: a guard arming after another had installed could not see the application's real `SIG_IGN` and never learned it, and a guard re-arming after another had installed over it read that other guard's handler as "an ordinary handler" and *discarded* what it had correctly recorded. Either way a process that set `SIG_IGN` got killed. **Fixed by moving the fact to where it belongs:** the ignored disposition is a property of the *process*, not of a guard, so it lives in a module-level `_IGNORED_AT_ARM` and is refreshed only from a disposition that is not any guard's.
   - **Ctrl+C was silently downgraded by the narrowing, and that was mine to catch.** With no chain, SIGINT took the `SIG_DFL` + `os.kill` path — so the GPU was restored but the process was *killed*: no `finally`, no `with` unwind, no atexit, and `main()`'s NVML close skipped. `_signal_restore` now raises `KeyboardInterrupt` for SIGINT, which reproduces the **default disposition's own behaviour** rather than calling back into whatever handler was installed. That distinction is the whole point — replicating a default is not chaining.
   - **Third consecutive pass with a test that cannot fail, and this one was in the tests I had just written for the narrowing.** `test_the_guard_never_calls_a_previous_handler` reported via `atexit`, which never runs after a `SIG_DFL` kill — so the assertion was unconditionally true and passed under the very chain it claimed to exclude. It now writes a witness file *from inside the handler*, synchronously, and that assertion is mutation-verified to fail. **Standing rule: mutation-verification proves a test moves, not that it is sound. Separately confirm each assertion CAN be false.**
   - Also from pass 12: `arm()` set `_armed` before publishing, so a transient `_write_state` failure left a guard believing it held the device with nothing on disk — and since `_armed` short-circuits `arm()`, the retry would reach hardware having never re-run `_check_not_busy`. A record with no `restored` key read as *settled* by every reader, so a foreign record naming a clock lock was reported not-stale and armed straight over; it is now required, and its absence means uninterpretable. And `lock_clocks` published a claim before checking the clock floor — same shape as the consent defect fixed in pass 8.
   - **Pass 13 (at `25bdc41`) found that a guard could write a record it never published.** `_surrender_claim` decided using the in-memory flag alone, with no "did I publish?" predicate — so a guard whose arm-time write had *failed* still wrote its clean record at exit, over whatever was there. Concretely: process P's publish fails, process Q arms and locks clocks, P exits, and P's atexit callback (registered before the failure) overwrites Q's live claim with `restored: true`. Q's locked GPU then has no evidence it is locked. Fixed with a `_published` flag — and the placement was the whole difficulty: cleared before the *publish* it still failed, because the stretch from building `self.state` to the signal-blocked section is interruptible (`threading.get_ident()` is a delivery point) and a handler there runs against the *previous* cycle's flag. It is now cleared before `self.state` is rebuilt.
   - **`raise KeyboardInterrupt` made a latent `_deferred_signals` bug reachable.** The mask was captured by the same call that applied it, outside the `try`. A pending signal dispatched between that call returning and the `try` being entered now unwinds — and the `finally` never runs, leaving **SIGINT and SIGTERM blocked for the life of the process**: no further Ctrl+C, no SIGTERM, no in-process restore on either. The mask is now read with a separate non-mutating call before the block, so `previous` is always valid by the time anything can raise. Before pass 12 this was unreachable, because every non-ignored delivery ended the process.
   - **Fourth consecutive pass with a test that cannot fail, and the two fixes for it were themselves wrong first.** `test_a_signal_during_arm_cannot_leave_it_armed_without_handlers` asserted `not (armed and not handler)` — but pass 12 deleted `_uninstall_handlers`, so `handler` is unconditionally true and the state it names is no longer representable; deleted. Then *both* replacement tests failed to discriminate on the first attempt: the mask test raised where the mask had never been applied (so nothing was left blocked either way), and the arm-window test fired its signal from `threading.current_thread()`, well before the window it was aiming at. **The lesson now recorded twice over: a mutation that leaves the suite green is the only proof a test is pinning anything, and it must be run against the specific defect, not a nearby one.**
   - **Deliberately single-thread, single-instance — a design decision made on evidence.** The guard refuses to arm off the main thread, refuses writes from any thread but the one that armed it, and refuses to arm while any unrestored record exists in the state file (whether the writing pid is alive — another guard is running — or dead — recovery is owed first). A future dynamic controller owns its guard on one thread.
     **Why:** four `hardware-safety-reviewer` passes on the earlier permissive design found 27 defects, and the large majority lived in machinery added to make concurrent use safe — an unlocked signal-path restore, write-depth and generation counters, per-pid state merging, an inter-process `flock`. That apparatus generated defects faster than it retired hazards; one of its own fixes introduced a **hang on the Ctrl+C path**, the exact failure the module exists to prevent. None of it was reachable by any real caller. The hazardous states are now unrepresentable rather than defended against, and the defending code is deleted.
     The residual same-thread hazard (a signal landing between recording intent and issuing the write) is closed by construction too: SIGINT/SIGTERM are **blocked for the duration of each hardware write** via `pthread_sigmask`, so a pending signal is delivered only once the write has settled. That replaced all the in-flight bookkeeping.
   - **What can and cannot be verified.** This driver exposes no `nvmlDeviceGetGpuLockedClocks` — there is no way to ask the device whether a clock lock is applied. So restore is **unconditional** (reset is a no-op on an unlocked GPU, giving idempotency for free) and stale detection has two labelled tiers: power limit is *verifiable from the device*; clock lock is *asserted by the state file only*. The state file (`results/gpu_guard_state.json`) is written and fsynced **before** the first hardware write, so a SIGKILL between locking and recording cannot lose the fact. `python -m joule_agent.gpu_guard status|restore` is the after-the-fact recovery path.
   - **Verification gate: CLOSED for the safety machinery.** Live kill-test passed on the 3060 Ti: locked at 1400 MHz, SIGKILLed mid-lock (uncatchable, so no handler ran), and the state file survived with `restored:false` and the lock recorded — which only works because the file is fsynced *before* the hardware write. `status` then correctly reported `stale:true`, `asserted_clock_lock:true`, `writer_pid_alive:false`; `restore` returned `reset_clocks:true` with no errors; `status` went clean. **What that run did NOT prove:** that the clock was ever actually applied to the device. There is no readback, so `reset_clocks:true` means the NVML call returned, not that the GPU was locked. See the separate lock-efficacy gate below.
   - **Verification gate: lock efficacy DEMONSTRATED at one point, NOT closed. Component 4 may be built; its numbers are not yet trustworthy.** NVML accepting `nvmlDeviceSetGpuLockedClocks` is not evidence the device honoured it; GeForce parts restrict some NVML writes. If the lock were a silent no-op here, every configuration in the static sweep would measure identically and the sweep would look like it ran while proving nothing. `tools/verify_clock_lock.py` settles it behaviourally: sustained synthetic load, SM clock sampled across baseline / locked / recovered phases. Measured at `df5c438` (dirty tree; driver 595.71.05, `GPU-647cc09d-5100-ea32-b0a2-59f6cf6acfc4`), 80 samples per phase:

     | phase | min MHz | max MHz | median MHz |

     | baseline (no lock) | 1905 | 1935 | 1920 |

     Eighty samples pinned at exactly 900 with zero variance is not producible by a confound — throttling, power capping and an idle card all produce *scatter*. **This card honoured this write.** What that does not establish is what the sweep actually needs.
     **What remains ungated, and why it blocks trusting the sweep's output rather than writing it:** (1) *n=1 on the clock axis.* One locked point shows a lock differs from **stock**. Every row of a sweep is labelled by a requested clock, so the sweep needs locks to differ **from each other** — a device that honours 900 and snaps everything else into one bin passes this gate and silently corrupts the whole grid. (2) *The power-limit axis has no efficacy gate at all*, and component 4 iterates it. A device-side readback proves the driver **stored** the cap, not that it **enforces** it. Until both are settled, `sweep.py` output is plumbing evidence, not a measured result.
     **The gate was run twice, and the reason is the point.** An earlier run at `c40a05a` returned the same verdict against a 1935–1950 MHz baseline — and this file went on recording it as "not yet run" for two days. But that artifact would not have closed this gate even had it been recorded. It established a *hardware* property (does this card honour the NVML write), which survives any refactor; the sweep needs a *code* property (does the current `gpu_guard.lock_clocks()` path reach hardware), and **22 commits touched `gpu_guard.py` between the two runs**, including the pass-5 restructure and the pass-12 handler removal. Same verdict, different claim.

Stock is the noisier control.

Artifacts now carry a `provenance` block — utc, git sha, a *tri-state* dirty flag, a **sha256 of `gpu_guard.py`**, driver, device UUID, and the exact load argv built by the same helper the phase runner uses so it cannot drift from what ran. ## Test-suite audit (the verification apparatus itself)

Four consecutive review passes found tests that could not fail — one written
during the narrowing, and in pass 13 *both* replacement tests were wrong on the
first attempt. At that point the suite is the least trustworthy part of the
module, so it was audited directly rather than reviewed again.

**Method.** Two batteries. (1) Stub out each protected-surface function in turn
(22 of them) and record which tests die; a test killed by nothing is a
candidate for pinning nothing. (2) For every survivor, hand-write the mutation
aimed at *what that test claims* and confirm it dies for that reason.

**Result: 112 tests, 93 killed by the blunt battery, 19 survivors, of which 17
pinned their claim under a targeted mutation and 2 did not.**

- `test_guard_claims_its_controller` asserted only `c.locked == (1400, 1400)` —
  the write happening, not the claim being taken. It survived `_require_claim`
  becoming a no-op, i.e. it never pinned its own name.
- `test_broken_power_restore_is_caught` was scaffolding that proved the suite's
  own assertions would trip; it survived the guard skipping the restoring power
  write *entirely*. Replaced by
  `test_a_silently_refusing_device_is_reported_as_a_clean_restore`, which pins a
  real documented limit: with no readback, a device that accepts a power write
  and does nothing is indistinguishable from success, and only the
  device-verifiable tier of `check_stale_state` can see it.

A static scan for structurally unfalsifiable assertions found 4 more:
`assert g._handler is g._handler` (trivially true), `check_stale_state(...) is
not None` (fails only by raising), an `or`-chain where either side satisfied,
and one premise-pin left implicit. All rewritten and mutation-verified.

**One correction to my own instrument, recorded because it is the same error
class:** the blunt battery first reported `test_recovery_resets_clocks_even_
with_no_state_file` as vacuous. It is not — the mutation was badly aimed and
left `result["reset_clocks"] = True` unconditional. A mutation that does not
actually break the property proves nothing about the test, exactly as a test
that cannot fail proves nothing about the code.

**Standing rule.** Mutation-verification shows a test *moves*. It does not show
the test is sound. Confirm separately that each assertion CAN be false, and
that the mutation used breaks the specific property named.

**This method now has an owner: `.claude/agents/test-integrity-auditor.md`.** It
was improvised once, under pressure, and found six tests certifying nothing --
one of which named the exact property it failed to pin. Component 4 is where
tests start guarding *results* rather than hardware state, and a vacuous test
there is a benchmark number nobody can trust. Report-only, like the other two
critics; it mutates source to do its work, so it restores what it touches and
reports the tree clean.

## Final pass: the contract, and what is accepted around it

The bar for the last pass was not "zero findings" but **the two contract
properties**: (a) the guard never claims `restored` while the hardware is or may
still be modified, and (b) it never destroys evidence of another live process's
claim. Findings were ranked CONTRACT or OTHER; CONTRACT was fixed, OTHER is
recorded here and accepted.

**One CONTRACT violation, property (b), now fixed.** `_published` says *this arm
cycle wrote a record at some point*; it does not say *the record on disk is
still mine*. The gap is reachable on the SIG_IGN path — the only one where the
handler returns and the interrupted frame **resumes**. A signal landing in the
unblocked stretch of `lock_clocks` (`_check_owner_thread` calls
`threading.get_ident()`, a delivery point) runs a full surrender, publishing
`restored: true` and disarming; another process then claims the device; and the
resuming frame writes `self.state` wholesale over that new claim and touches
hardware, having never re-run `_check_not_busy`. The newcomer's power cap
survives with no record that it exists. `_mark_touched` now refuses when the
claim has been surrendered, and it is called inside both writers' signal-blocked
section, so the check and the write it guards are atomic.

Worth naming: this is why the pass-13 audit did not catch it. Tests pinned the
resumed-frame property for `arm()` and had no analogue for `lock_clocks` /
`set_power_limit_mw`.

**Accepted, not fixed (OTHER):**

- `main()`'s `lock` path pre-checks consent and the clock floor but not
  privilege, so an unprivileged `lock` arms and publishes before failing. The
  residue is a *settled* record; it strands only on a hard kill inside that
  window.
- `restored: true` can be published alongside `clocks_locked: true` when a
  signal lands on the first write. Report-field inaccuracy only — every reader
  (`_check_not_busy`, `check_stale_state` tier 2, `wrote_power`) keys on
  `restored`, and recovery's clock reset is unconditional.
- `restore()`'s *failure* branch writes the state file without the `_published`
  predicate. Traced unreachable on every path — `_restored = False` is set only
  by `_mark_touched`, which is reached only after a successful publish — but
  unreachable-by-tracing, not by construction.
- Recovery's record write bypasses `_write_state`: no signal block, no unique
  temp name, no directory fsync, and a residual TOCTOU between its re-read and
  `os.replace`. No guard is armed in a `restore` process, so an interrupt there
  leaves temp debris and the original record intact.
- The `_check_not_busy` → `arm()` publish race remains narrowed, not eliminated;
  its window spans the `snapshot()` NVML round trip. Documented in the module as
  something not to build on.

**Property (a) holds independently.** All three writers of `restored: true` are
gated on a completed hardware restore, and `_mark_touched` always records the
debt before the write, inside the same blocked section.

## The CLI seam (where the mocked suite is blind)

`tools/cli_contract_check.py` exercises `python -m joule_agent.gpu_guard` as a
subprocess against a **real** device, asserting on exit code, message content,
and what each run left on disk. Run it unprivileged for the refusal paths; run
it with `sudo -E .venv/bin/python tools/cli_contract_check.py --root` for the
kill tests, which write real clocks.

**It exists because three defects reached committed code through this seam and
112 fake-NVML tests saw none of them.** `main()`'s `lock` path enters the
context manager — which arms, and arming publishes a claim — *before* checking
consent, and later before checking the clock floor; both left an operator-
visible record for a caller that was never allowed to write. And a mistyped
`--gpu` surfaced as a raw `NVMLError` traceback rather than an answer. The unit
suite constructs `GpuGuard` and `FakeGpuController` directly and never crosses
into `main()` or `NvmlGpuController`, so none of it was reachable there.

The rule that follows: **every refusal depending only on the arguments or the
caller — never on the device — must happen before the guard is entered.**

**The first version of that tool reported four false failures, and the bug was
the project's signature error in my own instrument.** It read
`nvmlDeviceGetClockInfo` and treated the *current* SM clock as a proxy for "is a
lock applied". It is not: an idle card sits at ~210 MHz whether or not it is
locked, and a card locked at [900, 900] sits at 900 when idle too. So the tool
reported **"GPU LEFT MODIFIED, still at 210 MHz"** — 210 MHz being precisely the
unlocked-idle value — and would equally have passed a card that was still
locked. A claim recorded without evidence supporting it, one layer further out
than the last one.

This driver exposes no `nvmlDeviceGetGpuLockedClocks`; the module says so and
builds its whole two-tier stale-detection around it. The only sound probe is to
**demand clocks and see whether they are capped**, which `verify_clock_lock.py`
already did and `cli_contract_check.py` now does: drive the synthetic load, take
the peak SM clock, and compare against a locked ceiling (1000 MHz) and an
unlocked floor (1200 MHz) with a wide dead band between them. The kill tests now
also refuse to start if the card is already locked, since every measurement
after that would be against a baseline that is not stock.

- **A green unit suite is not evidence about `main()`.** Two blocking defects
  in `sweep.py` — one of which meant the locked path had never executed once —
  were invisible to 241 passing tests because both lived in `main()` and no
  test imported it. That is now the third component where the CLI seam hid a
  defect the mocked suite could not see. So: any new CLI entry point gets a
  `*_contract_check.py` subprocess exercise, and logic that only `main()` can
  reach gets extracted until a test can call it.
- A review pass is not complete because an agent says it is. The gate is a
  green suite on the committed tree plus the named reviewer having actually
  run. `7700b0f` was committed claiming "187/187"; it was 259 passed / **8
  failed**, seven of them pre-existing safety tests that passed at `0a75638`,
  and the reviewer had never run (quota-blocked, then invoked with
  space-separated `--allowedTools`, which argparse ate). Reverted in `e0e5521`.
- Growth is a review signal. That commit took `gpu_guard.py` from 1,328 to
  3,749 lines re-adding the cross-process leases, at-fork hooks, machine-wide
  state mirrors, and capability tokens that the pass-5 restructure had
  deliberately deleted — and reproduced their failure mode. One of them,
  `_controller_write_access`, checked its token in `__exit__`, i.e. *after* the
  controller had already written the hardware: a write-then-refuse path, the
  exact shape the guard exists to make unrepresentable. If a safety fix cannot
  be expressed in tens of lines without new concurrency machinery, that is the
  signal to stop and ask, not to build it.
- Any numeric result or measured claim entering CLAUDE.md, `serve_flags.txt`,
  or a report: run measurement-skeptic before recording it.
- Before any measured result is recorded as evidence: run test-integrity-auditor
  on the tests that result depends on, then measurement-skeptic on the claim.
  That order matters -- the skeptic asks whether the evidence supports the
  claim, and the auditor asks whether the tests producing that evidence pin
  anything at all. A clean skeptic pass over a suite that certifies nothing is
  the shape of the `7700b0f` failure, one layer further out.

## Non-negotiable safety/honesty rules
- Never claim a specific efficiency percentage in code comments, README, or CLI output that hasn't actually been measured in that run. No placeholder "20-30%" claims anywhere.
- Report savings as a curve against p99 degradation, never a single point number in isolation.
- Always compare against tuned-static, never just stock default — beating stock default proves nothing.
- Auto-restore GPU clocks to default on any exit path (including Ctrl+C, exceptions).
- NVML clock/power writes require root/admin — fail with a clear error message if not running with sufficient privileges, don't silently no-op.

## Stack / language
- Python only for v1. No Rust, no Go, no C++ yet — the interesting part right now is the control policy, not the runtime performance of the control loop itself (100ms–1s loop, Python is plenty fast).
- Key libs: `pynvml` (install the official `nvidia-ml-py` package, not the third-party `pynvml` one — both provide a module named `pynvml`), `matplotlib` for plots. Note: the HTTP/parsing side has stayed stdlib so far — `workload.py` parses the Prometheus text format directly (no `prometheus-client`) and `loadgen.py` uses `urllib.request` (no `requests`), so neither has been needed yet — add either only when something actually requires it. vLLM's own benchmark scripts remain useful as *reference*, but component 3 chose not to depend on them (see above).
- Target GPU for local dev: whatever's available (e.g. RTX 3060 Ti) for plumbing/wiring only — it's underpowered and power-locked, so don't expect a representative number locally. The real number comes from a rented H100/H200 (RunPod/Lambda/Vast).
